# ADR-006 安全 hardening:密钥加密 / 审计日志 / 客户端幂等

状态:已接受 · 2026-11-03 · 关联:[ADR-002](ADR-002-storage-strategy.md)、[ADR-005](ADR-005-channel-registry-persistence.md)

## 背景

生产审计(P2 批次)发现三处与"多租户平台"定位不匹配的安全缺口:

1. `channels.api_key` 明文入库——拖库即拖走全部上游凭据;
2. 管理面动作(签发/吊销 key、注册渠道)无审计——"谁在什么时候吊销了这把 key"答不出;
3. 客户端重试无请求级幂等——超时重试会重复调上游、重复计费(账本唯一键只保证"不重记",不保证"不重执行")。

## 决策

**1. 渠道密钥静态加密(Fernet 对称)**

- 主密钥 `AGENTGATE_CHANNEL_ENC_KEY` 来自环境;prod 环境 Settings 校验器强制要求(与 admin_token 同款 fail-closed),dev 无密钥=诚实明文+启动告警。
- 密文带版本前缀 `enc:v1:`;存量明文行读取原样返回(非破坏兼容,重新注册即落密文)。
- 解密失败抛 InvalidToken 让渠道路由失败:**宁可该渠道不可用,不静默用错密钥打上游**——错误密钥等于把租户流量发给未知方。

**2. 管理面审计日志(只追加)**

- `audit_logs(actor/action/target/detail/created_at)`,五个管理动作与业务变更**同事务**写入——不出现"改了但没记",回滚连审计一起滚。
- 红线:raw key 与渠道密钥(含密文)不入审计——泄露审计面=泄露可用凭据;key.issue 只记 prefix。

**3. 客户端 Idempotency-Key(对齐支付/网关 API 惯例)**

- 作用域=租户+key+客户端 key;首次 SETNX 占锁(60s)→执行→响应入库(TTL 24h);重复请求回放(`x-idempotent-replay: true`),在途重复 409。
- 回放不重计费:账本记 `channel=replay`、token=0——可审计但预算/TPM 不动。
- 范围限定(诚实边界):**仅非流式**——SSE 响应体不可重放,带 key 的流式请求照常执行并留痕告警;错误响应不入重放库(视为瞬态)。

## 为什么不是别的方案

- **KMS/信封加密**:防"拖库可用"Fernet 足够;KMS 防的是"主机被攻破后内存中的密钥"——本机开发形态引入云 KMS 依赖不成比例,升级路径写在模块头(backlog)。
- **审计进日志文件而非表**:日志可改可丢、无法按 target 查询;表与业务同事务才有"必然有记录"的语义。
- **幂等靠客户端生成 request_id 去重**:已有(账本 `(tenant_id, request_id)` UNIQUE),但那只保证"不重记"——服务端重放缓存才是"不重执行";两者互补,不互替。

## 后果

- 正面:三条拷打面(拖库/审计/重试计费)各有一层可讲的防御,且每层有独立测试(7+4+4 项);prod 校验器让"部署了但裸奔"在启动时就失败。
- 负面:请求路径多一次 Redis SET(幂等锁)+响应后一次 SET(重放库存)——缓存/幂等类写,非计费路径,压测口径已含;密钥轮换需重启(诚实边界,模块头注明)。
- 风险:幂等锁在未捕获异常路径靠 TTL 自然过期(60s 内同 key 重试得 409)——可接受,TTL 上界明确。
