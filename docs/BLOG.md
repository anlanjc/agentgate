# 给 LLM 网关压测,我学到的两课(以及故障注入抓到的两个真 bug)

> 背景:我用 Python/FastAPI 自研了一个多租户 LLM 网关(agentgate),对标 LiteLLM 的核心
> 链路:鉴权、限流、计费、流式代理、故障转移。这篇记录压测阶段的两次"数字打脸",
> 和一轮真实多进程故障演练抓到的两个真 bug——它们共同证明一件事:
> **数字要带口径,可靠要靠拆家。**

## 第一课:客户端瓶颈会冒充服务端瓶颈

第一版压测数字:142 req/s,P50 335ms。按这个数字,这个网关是废物。

排查路径:先测 Redis——ping 0.12ms,不是它;再测裸 FastAPI 过 uvicorn——1.5ms,也不是它;
单独压网关的 401 路径(不碰任何依赖)——**依然 150ms**。问题锁定在"每请求必经的
Python 代码"上,而最重的嫌疑人是压测客户端自己:httpx 是纯 Python,单进程客户端
的 CPU 饱和后,服务端再快也测不出来。

换 aiohttp(C 解析器)后:同一网关从 142 涨到 321 req/s。客户端升级了,服务端一行没动。

**教训一:压测报告里的吞吐,是"客户端+网络+服务端"这条链的最小值。** 想知道服务端
真实容量,要么把客户端做到比服务端快一个量级,要么看同客户端同并发下的**差值**。

## 第二课:c=50 的中位差 120ms,是排队不是开销

修好客户端后,新问题来了:c=50 并发下,"过网关中位延迟 139ms − 直连基线 19ms = 120ms
附加开销",远超我 10ms 的目标。按这个数字,网关还是废物。

但 c=1 单请求实测只有 3.3ms。两数字矛盾吗?不——c=50 时单进程网关的服务能力是
串行的(每请求 ~2.8ms CPU),50 个并发排队,第 50 个请求等了 49×2.8≈137ms。
**这 120ms 是排队论,不是每请求代价。**

方法论修正:附加开销必须在 **c=1 无排队**条件下测。修正后:过网关 3.29ms − 直连
0.38ms = **2.54ms**,达标。而 c=50 的数字换个名字继续用——它叫"单进程吞吐上限",
解法是水平扩展:uvicorn --workers 1/2/4 实测 1.00x/2.15x/4.04x,近线性,因为所有
跨进程状态(限流桶、渠道健康、鉴权缓存)都在 Redis,进程本身无状态。

**教训二:P50 差值在并发下测出来的是排队延迟 + 开销,直接当"每请求开销"报出去,
就是用错误的口径自我抹黑。** 面试里讲压测,先讲口径再讲数字——统计位置、并发模型、
机器配置、测试时长,缺一项都值得被追问。

## 故障演练:kill -9 抓到的两个真 bug

压测证明"快",演练证明"稳"。我写了真实多进程演练:子进程起两个 Agent 服务注册进
网关,然后 kill -9 其中一个。

**bug #1:连接重置漏接成 500。** 进程被杀,内核 RST,httpx 抛 `ReadError`——
它不在我最初的异常分类元组里,直接穿透成未处理 500。修复:所有传输层异常统一捕获
走故障转移,再按类型映射(对端中断/连不上=502,真超时=504),并补了一个"真实 TCP
abort"回归测试钉死。演练后:kill -9 → 10ms 内自动切到备用渠道,客户端零感知。

**bug #2:空 Bearer 头被 httpx 拒。** 内网 Agent 服务没有 api_key,网关给它发
`Authorization: Bearer `(空值),httpx 直接抛 LocalProtocolError。修复:空 key
不发这个头。"没有凭证"和"空凭证"是两回事——前者是合法内网形态。

有意思的是,演练日志里还有一条 `usage_write_failed`(SQLite 文件锁,是此前被强杀的
孤儿进程遗留,环境残留)——它恰好证明:记账写库失败时网关按设计降级,没有崩。
**故障演练的价值不只是抓 bug,还有验证你设计的降级路径真的会按设计工作。**

## 收尾

现在这个网关的数字:每请求附加开销 2.5-3.7ms(双数据库口径分别实测)、4 worker 近
线性扩展、47×2 测试全绿(含双数据库方言)、真实 PolicyCompass 与 AskBI 两个 Agent
应用都接在它后面。最重要的是方法论:数字带口径,可靠靠拆家——这两件事,比任何
一个功能都更值得写进简历。
