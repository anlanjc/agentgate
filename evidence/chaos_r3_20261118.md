## S1 multiproc 双进程指标合并 × kill -worker(mark_process_dead 语义)—— 真缺陷所在

**实测语义链(prometheus_client 0.26.0,逐级 EXPLAIN 式取证)**:
1. 双 worker 各写 counter(3+5)→ 合并抓取 8.0(GATE-6 修复核心正确);
2. `taskkill /F` 杀 worker → counter 仍 8.0(**累计连续,上游 by-design**:counter/histogram 残留保留,删除反而制造虚假 reset);
3. **真缺陷:死 worker 的 Gauge 冻结**——应用两个 Gauge(USAGE_QUEUE_DEPTH/CHANNEL_COOLING)都是缺省 `all` 模式,合并输出带 `pid` 标签(`agentgate_channel_cooling{channel="c1",pid="2676"} 1.0`),死 pid 的文件被每次抓取**永久并入** → `sum()` 类告警永不恢复(渠道恢复后 sum 仍含死 pid 的冻结 1.0);
4. **上游 mark_process_dead 覆盖不到**:0.26.0 只 glob live 系(`_LIVE_GAUGE_MULTIPROCESS_MODES`),`all` 模式文件不清——实测 `after_mark_dead_gauge_still_there=true`;
5. GATE-6 的两道防线都够不到:k8s 下 uvicorn master 进程内重启 worker(非容器重启,Dockerfile rm -rf 不触发;非优雅停运,lifespan mark_process_dead 不触发)→ 残留存活期=整个容器生命周期。

**修复(当日)**:`metrics.cleanup_dead_process_files()`——worker 启动时(lifespan startup 挂钩)收尸:删属主 pid 已死亡且 mtime 老于 60s 的 gauge 文件(所有模式);counter/histogram 一律不碰;age 守卫防死 pid 复用误删;单进程口径 no-op;并发收尸幂等。存活探测跨平台零依赖(ctypes OpenProcess/POSIX kill 0)。回归 `test_killed_worker_gauge_residue_purged_on_next_worker_start`(断言链:合并 6.0→幻影在→收尸→幻影消失且 counter 仍 6.0→60s 守卫不误删)+ `test_lifespan_startup_calls_dead_file_janitor`(静态钉启动挂钩)。诚实边界:刚崩溃的 worker 的文件要等下一次 worker 启动才收(60s 守卫内不收),冷备单 worker 场景残留仍要到容器重启才清——比修复前(永不)严格改善。

## 装置教训(入册)

1. **textwrap.dedent 吃不齐缩进**:`python -c <dedent 后源码>` 因内嵌三引号字面量的零缩进行导致 common-prefix 失效 → IndentationError;改为写临时文件执行(混沌脚本 S1 教训);
2. **netstat 残留判定要按 LISTENING 过滤**:TIME_WAIT 客户端套接字会让"端口残留"误报(收尾清场判据);
3. **后台收尾的读时序**:并发槽释放挂在 BackgroundTask,响应返回后立即读计数会读到"尚未释放"的假象——断言前等后台跑完,否则会把良性时序误判为泄漏;
4. **prometheus_client 版本语义要实测**:mark_process_dead 的覆盖面(gauge live 系)与文档直觉不符,'all' 模式(应用缺省)完全不在其内——上游语义按实测入册,不按记忆。
