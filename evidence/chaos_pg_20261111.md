## 混沌抓到的真缺陷(当日修复,本批提交)

**P1:鉴权 DB 断连 = 裸 500(无信封、无 Retry-After)**。`app/auth/keys.py` 的 lookup 对 Redis 故障有降级(RedisError→直查 DB),对 **DB 故障无降级**——缓存 miss + PG 断连时 asyncpg 异常穿透 `_authenticate` → FastAPI ServerErrorMiddleware → 客户端拿到裸 `500 Internal Server Error`(真 uvicorn 实测,非信封;ASGITransport 下则直接异常穿透)。对照降级三分语义:缓存命中 200 / key 判定无效 401 / **无法判定(存储不可用)503**——"查不了"不等于"不存在",不落 401 也不落 500。

修复:`KeyStoreUnavailable`(keys.py,DB 块统一捕获、KeyNotFound/KeyInactive 显式放行)+ `_authenticate` 映射 `GatewayError(503, code=auth_unavailable, retry_after_s=5)`,与准入 `admission_unavailable` 同构。回归:`test_auth_db_unavailable_503_envelope` + `test_auth_cache_hit_survives_db_outage`(P2 语义:整个存储层换成连不上的引擎,缓存命中仍 200 零 DB)。

## 发现-边界(如实记录,不在本批修)

- **P2 故障窗内的账本行缺失**:缓存命中请求在 PG 断连窗内 200 正常服务,但 BackgroundTask 记账的 enqueue(先 INSERT task_records 再 XADD 的 transactional outbox)在 DB 提交处失败 → 该请求的 usage 行丢失(P4b 对账 4 行而非 5 行,`usage_enqueue_failed` 有 error 级日志含 request_id)。这是"账本事实来源在 PG"的推论而非 bug:PG 挂=无账可落;token 计量不丢(quota INCRBY 在 Redis,先于/独立于账本)。补强方向(未做,涉及 ADR-003 幂等键设计):usage 事件先 XADD、PG 恢复后由 sweeper 反向补落 task_records——需要新的设计轮,不宜混沌日热修。
- **恢复后首次 DB 使用撞已死池化连接**:terminate 全部后端后,连接池里的死连接是懒检测——恢复后首次检出报 `InterfaceError: connection is closed`,SQLAlchemy 断连失效+重检自愈(重试一次即恢复,实测 0.5s 内)。装置探针因此加重试;app 侧恢复后首请求(新 key 鉴权)实测 200。生产含义:连接池宜配 `pool_pre_ping` 或接受每轮故障后首个语句重试(未在本批改,独立于故障域语义)。

## 装置教训(同样入册,比 redis 域更贵)

- **进程级 kill+重启 postmaster 在本机 Windows 上装置不可信**:taskkill /T postmaster 后 pg_ctl/pgserver 重启,两次实测"postmaster status=ready 后 60s+ 新连接仍被拒"(WinError 1225,与 postgres 日志 `listening/ready` 矛盾;独立最小复现实验 start→connect→stop→restart→connect 却全通)——疑似与 app 进程同时重建连接池的时序相关,未深挖。**注入降档为 DB 层**:pg_hba reject(新连接认证期拒绝,superuser 也拦)+ `pg_terminate_backend`(既有池化连接真实 TCP RST)——对 app 是同一条异常路径(asyncpg 连接类异常→SQLAlchemy→网关降级语义),P1-P3 的进程级版本也已先行实测(500 实锤来自那批),结论不受注入档位影响。
- **pg_ctl start 用 `capture_output=True` 会挂死**:pg_ctl 起的 postgres 继承 stdout 管道且长活,`timeout` 杀掉 pg_ctl 杀不死孙进程,`communicate()` 永等管道 EOF → 整个脚本挂死。子进程一律 DEVNULL。
- **崩溃恢复 fsync 数据目录时,-l 日志放 pgdata 内 → Windows 共享冲突**(`sharing violation`)重试 30 秒。服务日志必须放 pgdata 外。
- **探针自身会撒谎**:db_alive 探针曾用 URL `?timeout=5` 传连接超时,SQLAlchemy asyncpg 方言把 query 里的 timeout(str)与内部默认(float)合并 → `TypeError: float + str` → 探针"永远探不通",把健康的恢复段误判为"PG 起不来"并连带否定了整个重启路径(教训修成 `connect_args={"timeout": 5}`)。**混沌装置的每一次 FAIL 都要先区分"被测对象挂了"还是"探针挂了"——本次 3/8 的 FAIL 全是探针/装置问题。**
- **admin 恢复通道必须在注入前建立**:reject 写入对新连接的生效时序不可依赖(reload 前即可能生效),注入后再连 admin 会把自己拒之门外。
